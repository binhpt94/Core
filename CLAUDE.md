# CLAUDE.md: rules for AI agents (Claude Code, Codex, Cursor, ...)

Unity sample: **"Quiz Defense"**: an addition quiz (pick 1 of 3, 10 s per question) where random slimes walk to your base;
a correct answer zaps the nearest one, a wrong answer or time-out enrages them. Deterministic fixed-tick simulation (20 Hz).
Unity 2022.3 LTS / Unity 6 · C# 9 · uGUI · UniTask 2.5.10 · NUnit.

**Rules are enforced by tools, not by memory.** After every edit a hook checks the file (≈0.1 s, silent when clean);
you cannot finish while the gate is red; commits, Play Mode, builds and CI run the same checks.
When a hook prints `ARCHxxx path:line ...`, fix it right away and read **only** that rule's section in `Docs/RULES.md` if needed.

## 1. Before you change anything
1. `Docs/Architecture/overview.md` (generated system map) → `Docs/Architecture/Features/<F>.md` for the feature you touch
   (1-hop diagram, public face, state machine, DI) · the feature's `README.md` · its tests.
2. Need more? **Query, don't read code:** `test-gate.sh graph feature <F>` · `graph impact <F>` · `graph di <F>`.
3. From other features, open only their `Contracts/` (and `Assets/Public/`), never their internals.
4. `Docs/ARCHITECTURE.md` explains the why (read once, when the rules surprise you).

## 2. Commands
```bash
dotnet test Tools/LogicTests                          # inner loop, seconds: rules + all pure tests
./Tools/test-gate.sh check                      # static rules on changed files, milliseconds
./Tools/test-gate.sh plan                       # which gates this change needs
./Tools/test-gate.sh run                        # DEFINITION OF DONE (exit 0)
./Tools/test-gate.sh refs Assets/_Game/Features/X   # before deleting/moving a feature: must print nothing
./Tools/test-gate.sh deadcode [--all]               # ARCH033: code nothing references (changed files; --all = old debt)
./Tools/test-gate.sh graph --write              # after changing asmdefs/contracts/state tables (ARCH090 tells you)
./Tools/test-gate.sh new-feature Name [--contracts] # new feature that already passes every rule
./Tools/test-gate.sh new-view Feature ViewName      # view/popup testable in isolation (view, layout recipe, fixtures, cases)
```
- `UNITY GATE NOT RUN` → say "Unity tests pending" in your report. Exit **4** → stop, don't retry, report.
- The Stop hook runs `run` for you; if it blocks 3 times, stop and report the failures verbatim.

## 4. Rules (full list with fixes: Docs/RULES.md)
| Area | Do | Never | IDs |
|---|---|---|---|
| Assemblies | pure = `noEngineReferences`; cross-feature only via Contracts; Bootstrap uses Installers | GUID refs, cycles, Bootstrap→Logic | 001–012 |
| Access | Logic `internal`; `InternalsVisibleTo` only to own `.Unity/.Tests/.Editor`; public = Contracts + Installer/Module/asset entry | public Logic types, public mutable fields, changing `PublicApi.txt` | 020–023 |
| Shape | small types, composition, only what the tests need | `partial` (except Generated/ + `// <auto-generated>`), files > 300 lines, unreferenced code | 030–033 |
| Calls | interfaces, typed events, serialized refs, `Animator.StringToHash` | `SendMessage`, `Invoke("..")`, reflection, `Find*`, `Resources.Load`, singletons | 040–044 |
| Pure code | `IRandom`, `IDelay`, `lifetime.Run` | UnityEngine, `DateTime.Now`, `Task.Delay`, `.Forget()`, `.Application/.Unity/.Editor` namespaces | 050–054 |
| State/async | per-round state, `Lifetime` tree, `UniTask` returns | mutable statics, static events, `async void`/`UniTaskVoid` | 060–062 |
| Determinism | `IRandomStreams.For("purpose", keys)`, integer ticks, commands, `StateHashBuilder` | `System.Random`, `DateTime.Now`, `GetHashCode()`, floats in Domain/Simulation, views touching Domain/Simulation | 051, 055–057 |
| Unity data | config in the feature's ScriptableObject; references **required by default** (`[OptionalReference]` to opt out) | primitive `[SerializeField]` config on MonoBehaviours (`[VisualTuning]` for pure visuals), public SO state | 070–073 |
| Assets | `Assets/Private` by default; others reference only `Assets/Public`; scene = GameRoot + layout | cross-feature private refs, scene data overrides, `Resources/`, binary serialization, YAML assets (`.prefab/.unity/.asset`...) without `.meta` | 080–084 |
| UI & dev tools | static layout in `Views/<V>/<V>Layout.cs` or the prefab; view moves only from data (`// layout: dynamic`, no constants); every view has fixtures (incl. `smoke`) + cases; cheats = scenarios (commands) in `DevTools/` | layout constants in views/installers, setting state for a cheat, runtime code referencing `DevTools` | 100–102 |
| Art slots | contracts in `Logic/Domain/<F>ArtSlots.cs`, id `F.Name`; bindings name real slots of their feature | art prefab refs from gameplay, a binding to a typo | 120–121 |
| Files | known layout; scratch in `.scratch/`; move assets with their `.meta` | loose/temp/copy files, scenes outside Scenes/, dangling GUIDs | 130–132 |
| Docs & vendors | regenerate the overview; keep doc names/paths real; SDKs only via their adapter's Contracts (`IAdsService`) | editing generated docs, vendor code or `Tools/ArchitecturePolicy.txt`; using an SDK outside its adapter | 090–095 |

State machines are `Transition<TState>` tables (see `QuizSession.Transitions`): the code enforces them and the diagram is generated
from them, so add the row instead of a bare `State = ...`. Rows must be `new Transition<E>(E.A, Trigger, E.B)` or `new(E.A, Trigger, E.B)`
with a literal or same-file `const string` trigger; anything else is ARCH090 (the generator refuses to guess).

Async specifics: every async method takes a `CancellationToken`; capture it before the first `await`; after every `await`
re-check `token.IsCancellationRequested || !IsStillCurrent(...)` (outside simulations); SDK callbacks go through an adapter that switches to the main
thread and checks the lifetime.

## 5. Prefabs & scenes (you cannot drag & drop; don't fake it)
- **Never hand-edit `.unity` / `.prefab` / `.asset` / `.meta` YAML** (denied).
- UI structure = **prefab recipe in code** (`QuizViewLayout`) → `Tools/Game/Prefabs/...` or
  `-executeMethod Game.MathQuiz.EditorTools.QuizViewPrefabRecipe.CreateBasePrefab` builds `*.generated.prefab`.
  Artists skin a **Prefab Variant**; the asset entry points to it.
- A component references only objects **inside its own prefab** or assets of its own feature; cross-object wiring is Bootstrap's job.
- Scenes contain `GameRoot` (+ layout overrides). Data never lives in a scene.

## 6. Determinism (simulation features)
- Gameplay that changes over time is a **simulation** in `Logic/Simulation`: `Step()` once per tick, inputs only as
  **commands** (applied at the start of the next tick, in order), integers only, no Unity, no async, no clock.
  The presenter turns frames into ticks with `TickScheduler`; frame rate never changes the result.
- Randomness: one **keyed stream per purpose** (`streams.For("arena.hop", round, enemyId, tick)`). Never share a sequential
  RNG between systems; never derive seeds from `GetHashCode()`. Stream names are part of the replay format: don't rename them.
- Every state that influences the future goes into `StateHash()` (fixed order, collections by id).
- Bugs: a replay (`.replay.txt`, from the error dump or *Tools > Game > Debug > Save Replay*) dropped into the feature's
  `Tests/Replays/` becomes a regression test. A golden replay failing means gameplay changed: if intended, **ask the owner**
  to regenerate (`GOLDEN_WRITE=1 dotnet test Tools/LogicTests`, run alone: the owner answers yes/no) and review the diff. Changing rules on purpose? Bump `SimVersion`.

## 7. UI: views, popups, components
- New view: `test-gate.sh new-view <F> <V>`. A view only renders view models and raises events.
- "Check how it looks in state X": add a **scenario** (`DevTools/Scenarios`, commands only) or an **edge fixture**
  (`DevTools/Fixtures`, hand-made view models). Never a `CheatX()` that sets fields. Preview: *Tools > Game > UI > View Preview*.
- What runs is decided by file role (`test-gate.sh plan` shows it): a layout change runs only that view's layout gate
  (Unity EditMode, `-testCategory View:F.V`: L2 constraints on every fixture × device, L3 text snapshot).
- L3 snapshot differs after an intended layout change → **ask the owner** to regenerate (`LAYOUT_WRITE=1 ./Tools/run-unity-tests.sh …`, run alone: the owner answers yes/no)
  and show them the diff lines. L2 violation (`L-SAFE`, `L-OVERLAP`, `L-TEXT`, `L-TOUCH`) → fix the recipe/prefab, never the check.

## 8. Tasks, scope and the flight recorder
- **Before editing anything:** `./Tools/test-gate.sh task start "<what>" --feature <Feature>` (one feature = active at once).
  Without an active task, or outside its scope, writes are **blocked before they happen** (PreToolUse).
- Need another feature, a path outside features, or to change what a test expects? `task request --feature G | --path P | --tests "<why>"`
  and tell the human; only they approve: `task approve` in their terminal, or you run `./Tools/test-gate.sh task approve` alone and
  they answer yes/no in Claude Code (see Owner commands below). Keep working inside the current scope.
- **Need another module to change? Never ask its session by message** (SendMessage is logged; a request that way approves nothing).
  `task need <F-ID|Module|Core> "<what, why>" [--api "<PublicApi line>"]…` files `CR-n`; keep working against a fake in your own
  feature (it owes CR-n until delivered). New types only: the gate approves at once and your task may write B's Contracts (exactly
  those PublicApi lines + a skeleton). Breaking: another session rules (`cr rule CR-n keep|reject|ask "<why>"`). No API (meaning) or
  breaking Core: the owner (`cr decide` loop in their terminal, or `cr decide CR-n approve|reject "<why>"` → their yes/no). An approved CR is a requirement of B: `task start … --from CR-n` (roles as usual).
  A CR filed in another worktree is visible here at once; starting on it copies its lines into your branch: commit them.
- A task without `--req`/`--from` is maintenance: changing a feature's `Contracts/` or `Logic/Domain/` there, or turning one of its
  `[Covers]` tests from red to green, is `UNTRACED_CHANGE` at Stop.
- Edits made through Bash (sed, scripts) are observed via git snapshots and judged like Edit. Undoing a change is always allowed.
- At Stop: every changed file must be in scope, tests must not be weakened (fewer asserts/tests, new Ignore/Assume/#if), then the gate.
- **MCP (Unity, Blender):** read tools (get/list/find/screenshot/run_tests) are free. Tools that change things need a task and
  are observed like Bash: every file they change is yours (scope, rules, Stop), including a prefab Unity saves later. Tools that
  run arbitrary code (`execute_blender_code`, `execute_menu_item`, ...) are blocked: use the specific tool; if none can do it,
  `mcp allow exec <tool>` (an owner command, below; `Tools/mcp-policy.txt` is theirs). Save scenes/prefabs in the editor before you finish: the gate only sees the disk.
- **Red because of a HUMAN** (their plan typo, misplaced file, inspector/gameplay tweak, removed assert: the event log proves
  you didn't write it): Stop lets you finish and lists it as "waiting for a HUMAN". It is **not yours**: don't fix it, don't work
  around it, just mention it in your final message. The human gets the commands in their terminal and on the dashboard.
- **Owner commands** (`task approve`, `roadmap accept R`, `art accept S` | `art accept --draft "FILE"`, `cr decide CR-n approve|reject "why"`, `tests unseal R "why"`,
  `tests grandfather`, `api accept <Game.Core|Game.F.Contracts>` (ARCH023 baseline), `policy vendor add k=v… | update <id>`
  (ARCH093/094), `mcp allow read|write|exec <tool|'prefix*'>`, `GOLDEN_WRITE=1 …`, `LAYOUT_WRITE=1 …`): only when the owner asked for it or a gate tells you to. Run the
  command **alone** (no `;`, `&&`, `|`, `$(…)`, `bash -c`); the hook shows the owner what the gate computed and they answer
  yes/no. One yes = one run of exactly those args (`OwnerAsk`). Chained/wrapped forms stay blocked; a "no" is final: don't retry.
  The dialog text (plain Vietnamese: what, content, status, Yes/No, what to check, undo) is `OwnerAskText`; show it to the owner
  beforehand with `./Tools/test-gate.sh owner-preview <args>` (`golden`, `layout …` for baselines); it asks and grants nothing.
- `.agent/` (event log, task) is written only by the gate. Your final message is recorded as a CLAIM and shown next to the evidence.
- Useful: `task show` · `events tail 20` · `roadmap next` · `task close` when done. Ask these commands (short, computed answers);
  never read `.agent/`. `Dashboard/Data/` is the human's: prefer the commands; when you need the raw output (e.g. which Unity
  test failed in `EditMode.xml`), Grep/Read exactly that file: the owner is asked yes/no, one yes = one read (no `cat` via Bash).

## 9. Roadmap: what to build (Docs/Plan/features.md, owned by the human)
- **Don't plan from memory.** `./Tools/test-gate.sh roadmap next` says what can be done now (parallel lanes, the exact
  `task start ... --req R-...` command); `roadmap status [F-ID]`, `roadmap gaps` show everything computed from tests.
- Start planned work with `--req`: the task's scope comes from the feature's `[modules]`; blocked items are refused
  (hard dependency not DONE, contract not frozen, or not `[rush]`). Rush prints the integration debt it creates.
- New tests that implement a requirement get `[Covers("R-ID")]` (`using Game.TestSupport;`). Unknown ids fail ARCH111.
- **Plain requirements (default):** one task (`task start … --req R-…`, no `--role`) writes the tests and the code; VERIFIED when
  the tests pass. `task close` prints what the tests you added/changed check (`tests summary [R-ID|F-ID]` any time): keep test
  names and asserts readable, that summary is what the owner reads.
- **Separation of duties (`[critical]` requirements only):** the session that writes their tests never writes their code. `roadmap next`
  gives three lanes, each with its exact command:
  - `--role tests`: write tests in `Features/<F>/Tests/` plus a skeleton (new members with `=> default` bodies, never `throw`), commit,
    then `./Tools/test-gate.sh tests seal R-…` (lint: real asserts; red first: they must FAIL ON AN ASSERTION, twice the same).
  - `--role impl` (another session): write the code until the sealed tests pass. `Tests/` is read-only to you. A test you think is
    wrong: `tests dispute R-… "<what R- says vs what the test demands>"` and work on another requirement; never edit it.
  - `--role arbiter` (a third session): `tests rule R-… keep|fix|ask "<why>"`. fix = correct the test and seal again; ask = the
    requirement is ambiguous: propose the new wording to the owner (features.md yes/no). The 3rd dispute of one R- becomes ask.
  - A requirement counts (VERIFIED) only with live, unchanged, undisputed sealed tests. Sealed tests that are red because the code
    isn't written yet are reported by the gate, not a failure. `tests unseal` / `tests grandfather` are the owner's (yes/no only).
- **Adding or changing features/requirements (only when the owner asks):** write the whole proposed file to
  `.scratch/features.draft.md`, run `./Tools/test-gate.sh roadmap draft .scratch/features.draft.md` and show the owner its list
  of changes (`+ R-…`, `~ R-…`, `- R-…` with their text). Adjust with the owner until agreed, then write `Docs/Plan/features.md`
  with **Edit/Write**: the gate checks the result and Claude Code asks the owner yes/no; one yes = one write. A single new R- may
  skip the draft. `Docs/Plan/Core.md` (core idea) works the same way: show the owner the proposed text, then Edit/Write → yes/no
  with the changed lines. `Docs/Plan/Notes.md` (owner's notes) is written freely on request. Never write features.md or Core.md
  through Bash/scripts (always a breach). Unsure? `roadmap propose "<what and why>"`.
  `Docs/Plan/accepted.txt` stays denied (written only by `roadmap accept`, the owner's yes/no).
- If Stop says **STALE task**: the human changed a requirement you were working on. Re-read it, adapt code and tests,
  `task close`, start again from `roadmap next`.
- Syntax and statuses: `Docs/PLANNING.md`.
- **Story · Gameplay · Art:** story goals are `[story]` requirements checked by design-lint tests over content data
  (archetypes in `Logic/Domain`), not hard-coded content. Art goes through **slots** (`<F>ArtSlots.cs` contracts; graybox is
  generated from them): never reference art prefabs from gameplay, never resize/retime gameplay to fit art (change the
  contract → ask the human). Candidates need only the automatic art gate; `art accept` (owner, yes/no) is for the final only.
  Owner says "sync file duyệt art": Read the newest `~/Downloads/art-accept.draft*.txt` (or the path they give), then run
  `./Tools/test-gate.sh art accept --draft "<absolute path>"` alone; never edit the draft.
  Art never blocks dev: art debt is for artists and never holds DONE, dependants or `task start`.

## 10. Files: where things go, what is junk
- **Scratch work goes to `.scratch/`** (gitignored, outside Assets/, never imported): throwaway scenes, dumps, notes.
  Never test with a scene in `Assets/` (use EditMode stages); never leave `New Scene`/`* copy`/`*.orig`/`*.tmp` files.
- Every file must sit in the known layout (ARCH130); junk is ARCH131. Hooks flag it on the edit; Stop names what YOU left.
- Clean up your own leftovers: `./Tools/test-gate.sh files clean --junk --yes` (deletes only untracked files an agent wrote and
  nobody touched since; never tracked files, never a human's). After a crash: `files orphans` / `files clean --orphans --yes`.
- Move or rename assets **in Unity** (or `git mv` file + `.meta`). ARCH132 = a reference to a GUID that no longer exists;
  its message prints the exact fix: run it only if you made the move, otherwise tell the human.
- New `.cs` files and folders need **no** `.meta` to pass the gate (only YAML assets do, ARCH084); never write one yourself:
  Unity creates it on the next open. Split code into new files freely; don't stuff it into an existing file to avoid a `.meta`.

## 11. Testing async & lifecycle
`QuizHarness` + `ManualFrames`/`FakeClock` (tests drive frames and time; `Ticks(n)`, `Seconds(n)`), `IgnoreCancellation = true` for sources that ignore tokens, `[Category("Lifecycle")]`
for replay/dispose/stale-result tests, assert `Logger.Errors` empty in `TearDown`. C# 9 + NUnit 3.5 APIs only.

## 12. Workflow
1. Restate the task; `roadmap next` → `task start ... --req R-...` (`[critical]`: `--role tests|impl|arbiter`; `--feature F` for unplanned maintenance).
2. `test-gate.sh plan` → failing test first, then the code (`[critical]`: role tests commits and runs `tests seal`; role impl implements until the sealed tests pass) → `dotnet test Tools/LogicTests`.
3. Unity-side changes are batched; `test-gate.sh run` once at the end.
4. Update the feature README if API/lifetimes/invariants changed.
5. Report: what changed, which gates ran / didn't, anything you couldn't follow and why.

Write only the code the requirement's tests need: nothing "for later", no option, parameter, stub or TODO nobody uses yet;
the simplest code that passes is the right one (ARCH033 flags what nothing references). A requirement the owner marks
`[dropped]` is cleaned up with `task start --retire R-X` (`roadmap next` lists it first; Stop holds until it is gone).

## 13. Never
- Touch protected files (`Tools/`, `Assets/_Game/Architecture/`, `Assets/_Game/Tests/Architecture/`, `**/PublicApi.txt`,
  `Tools/ArchitecturePolicy.txt`, `Docs/Architecture/`, `Assets/ThirdParty/`, `Assets/Plugins/`, `.claude/`, `.github/`, `ProjectSettings/`,
  `Assets/_Game/Core/Editor/`, `**/Tests/Replays/`, `**/Tests/Layout/`, `Docs/Plan/accepted.txt`, `Docs/Plan/art-accepted.txt`;
  `Docs/Plan/features.md` and `Docs/Plan/Core.md` only via Edit/Write after the owner's yes, see §9):
  they are denied to you and CODEOWNERS-reviewed. New vendor: `policy vendor add …` (owner yes/no). Exception: ask the human.
  Core maintenance (changing the rules or tools themselves): `task request --core "<why>"`; only after the human approves it
  may that task edit protected files (never `.agent/`). It ends with `task close`.
- Bypass a gate: `--no-verify`, changing `core.hooksPath`, `[Ignore]`, weakening a test, disabling the Play Mode gate.
- Edit outside the task's feature "while you're at it", or add packages / DI frameworks / global event buses without asking.
